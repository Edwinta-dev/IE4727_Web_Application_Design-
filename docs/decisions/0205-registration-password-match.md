Status: implemented · Issue: #205 · Date: 2026-10-27

## In short

Registration shows a password mismatch beside Confirm password while the visitor types. Correcting the mismatch clears the warning immediately.

## How it works

The registration page gives the confirmation field an accessible description that points to its inline error. Once the visitor edits that field, input and blur events on either password field compare their current values. A mismatch shows the existing warning text and marks the confirmation field invalid. A match clears both. The submit handler still checks the values, and the server continues to reject mismatches.

## Main design choice

Reuse the existing inline error span and registration validator, with a small client-side touched flag. A separate status element would duplicate feedback and could disagree with the submit error. The flag leaves the untouched confirmation quiet while preserving feedback if the visitor clears it after typing.

## Problem and constraints

Previously the password mismatch appeared only after submitting registration. The base app allows local vanilla JavaScript and requires the existing server validation to remain authoritative.

## Alternatives considered

- Show an error before the visitor reaches Confirm password: rejected because the empty field would be marked wrong before interaction.
- Use the browser's custom validity message: rejected because it would not use the page's existing inline error position and message.

## Trade-offs

The client-side warning depends on JavaScript. The form still reaches the existing server-side check when JavaScript is disabled.

## Key parameters

- The warning text is `Passwords must match.`
- The mismatch border uses the shared `--c-danger` token; the existing keyboard focus ring remains visible.

## Assumptions

Editing Confirm password once is enough to start live comparison, including when its value is subsequently cleared.

## Edge cases

- Editing Password after Confirm password has been touched updates the warning.
- A matching pair removes the warning and `aria-invalid` immediately.
- Matching passwords shorter than eight characters remain subject to the existing length validation.

## Breaks or needs follow-up

None.

## Traps

- Keep the server's `matches:password` rule in registration processing.
- Keep the existing submit validation and avoid showing mismatch before the confirmation is touched.
- Keep the focus-visible ring when the invalid border is displayed.

## Components

- `clinic-base/register.php` links the confirmation input to its inline error and reflects a server error with `aria-invalid`.
- `clinic-base/assets/app.js` compares both password fields during typing, blur and submit.
- `clinic-base/assets/css/style.css` colors the invalid confirmation border with the danger token.
- `tools/ui/issue205.test.mjs` checks live mismatch, correction, clearing, submit feedback and the no-JavaScript page in Chromium at 1280 and 390 pixels.

## Changes outside the scope

The browser regression test and this decision record are required verification artifacts. No other application component changed.

## How it was verified

`node tools/ui/issue205.test.mjs` checks live behavior at both requested widths. `php tests/run.php` checks the full project suite. Before and after screenshots are stored under `UIPROBLEMS/after/iter8/create-account-password/` and inspected.

## Not verified

## To change this

## Rollback

Remove the live listeners, accessible inline error association, invalid border rule, browser regression and this record together.
