Status: implemented · Issue: #193 · Date: 2026-10-16

## In short
Choose a date first, inspect its availability, then set working hours or block an individual time.

## Problem and constraints
The existing editor placed schedule generation before date selection and mixed its purpose with individual slot controls. This is a visual pass: the generate and toggle POST actions, validation, cancellation, notification, CSRF and redirects stay in place. The schema has no block reason or period record.

## Main design choice
Keep the existing 30-day calendar rather than build the suggested week-by-hour grid, and give each day a compact status proportion bar with a text legend. Put the selected day's slot controls and working-hours form in separate columns on desktop, and in that order below the calendar on mobile. This uses the existing date selection and slot actions. A new week-by-hour editor would imply range blocking and reason storage that the current server contract cannot perform.

## Alternatives considered
- A week-by-hour grid: deferred because the current actions address one existing slot at a time, and no reason field can be persisted.
- A separate block form with date and time inputs: deferred because it would need new server validation and mapping to existing slots.

## How it works
The calendar's state bar shows relative Available, Booked and Blocked counts; its accessible day name retains exact text counts. The selected day shows individually labelled slots. A booked slot's confirmation names the affected patient, while the existing required checkbox and server check still gate cancellation. The date GET form submits on change with JavaScript and retains its submit button for use without JavaScript.

## Traps
- Booked patient names need escaping in both visible copy and the form data attribute used by the confirmation dialog.
- The calendar is visually ordered first through CSS; the existing source order remains for schedule page regression checks.
- A blocked slot can be reopened, but the current data model cannot store a reason or undo a whole period.

## Components
- `clinic-base/doctor/schedule.php`: clarifies section copy, shows status proportions, names the patient before blocking a booked slot, and loads `app.js` (it was previously loaded only on the doctor list and registration pages).
- `clinic-base/assets/css/style.css`: orders and sizes the calendar, slot list and working-hours form across desktop and mobile.
- `clinic-base/assets/app.js`: submits the existing date GET form after a valid date change.
- `tools/ui/issue193.test.mjs`: checks the 1280/390 layout order, the named-patient confirmation, the cancellation and notifications, and the date auto-submit in Chromium.

## Changes outside the scope
This record and the browser test are required verification artifacts. No other app page changed.

## Trade-offs
The working-hours form still generates up to 30 days because that is the existing action. Blocking remains per slot. The desktop skip-days list scrolls horizontally to keep the form compact.

## Key parameters
The calendar covers 30 days and keeps seven weekday columns; the layout collapses to one column below 56rem.

## Assumptions
The seeded and generated slots are the source of truth for day counts and available actions.

## Edge cases
Elapsed slots remain read-only. A booked-slot submission requires the existing confirmation checkbox, and the server rechecks current slot ownership and status.

## Breaks or needs follow-up
The database cannot store a block reason or a blocked period. A later iteration would need an agreed server action before adding those controls.

## Not verified
No physical screen-reader session was run.

## To change this
If period blocking is added, define its persistence and cancellation rules first, then update the editor and its test together.

## Rollback
Restore the schedule markup, styles and date change handler together.
