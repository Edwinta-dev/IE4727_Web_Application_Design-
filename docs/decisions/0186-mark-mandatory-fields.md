Status: implemented · Issue: #186 · Date: 2026-10-16

## In short
The registration, login, booking, and schedule forms show a red asterisk beside every field their server handlers require, with a short key at the start of each form.

## Main design choice
Keep the existing forms and server validation. Add an `aria-hidden` visual mark to each required label or radio-group heading and pair each editable required control with `required` and `aria-required="true"`. The shared CSS in `clinic-base/assets/css/style.css` colors the marks with the existing danger token and spaces the notes without changing the form layouts.

## How it works
`clinic-base/register.php` marks common account details and the required fields for each role. Its existing role switcher disables the inactive fieldset. The form uses `novalidate` so a no-JavaScript submission still reaches the role-specific server validation when the other fieldset is present. `clinic-base/index.php` marks both login fields. `clinic-base/book.php` marks the doctor, appointment time, and new-visit reason choices. `clinic-base/doctor/schedule.php` marks the schedule generator, date filter, and booked-slot cancellation confirmation.

## Traps: why the obvious fix is wrong
- Requiring both registration role fieldsets in native validation would block a no-JavaScript patient or doctor submission on fields for the other role.
- The booking time-range filters are optional; their previous `required` attributes contradicted the server behavior and were removed.
- The date and schedule-generator hidden values have no visible labels to mark; their visible editable controls receive the marks.

## Components
- `clinic-base/register.php`: account and role-specific field markers.
- `clinic-base/index.php`: login markers.
- `clinic-base/book.php`: booking choice markers and optional filter correction.
- `clinic-base/doctor/schedule.php`: schedule and cancellation markers.
- `clinic-base/assets/css/style.css`: shared marker and note styles.
- `tests/test_issue161.php`: keeps the prior reason-field regression aligned with its updated markup.
- `tools/ui/required-fields-186.test.mjs`: Chromium checks markers, attributes, optional fields, role switching, and no-JavaScript server validation.

## Breaks or needs follow-up
None known.

## Problem and constraints
Issue #186 asks users to see which fields are mandatory before submitting. The base app must keep server-rendered forms, existing validation, and the eleven-page budget.

## Alternatives considered
- Relying on native browser validation alone: rejected because asterisks and the form key must be visible before a submit attempt.
- Dynamically removing `required` from inactive registration fields only in JavaScript: rejected because the form must remain usable with JavaScript disabled.

## Trade-offs
Registration delegates submission errors to the server with `novalidate`; the required attributes still expose field requirements to the DOM and assistive technology. This preserves validation for both account roles without depending on JavaScript.

## Key parameters
The red mark uses `--c-danger`. The note reads `* required`. Chromium acceptance checks a 390-pixel viewport and verifies field attributes; before and after captures exist at 1280×800 and 390×844.

## Assumptions
The server-side validation in `clinic-base/actions/register.php`, booking actions, and `clinic-base/doctor/schedule.php` remains authoritative if a request bypasses the form.

## Edge cases
Patient allergies, booking time filters, and schedule skip days remain optional. A doctor submission with JavaScript disabled and empty doctor fields returns the existing server error summary.

## Not verified
Physical screen-reader announcements were not tested.

## Rollback
