Status: implemented · Issue: #187 · Date: 2026-10-16

## In short
Patients can select "I'd rather not disclose" when creating an account. The choice survives registration and appears as entered on the doctor visit page.

## Main design choice
Extend the existing `patient.Gender` enum through `schema/002_migrate.sql`, then add the same literal to the registration select and server validation, rather than replacing the enum with free text. This keeps existing values and the column name intact while retaining the data constraint.

## How it works
The registration form submits the selected value to the existing POST handler. The handler validates it against the four allowed values, and the account model stores it without translation. The patient model reads the stored value; the visit page already escapes and displays it.

## Traps: why the obvious fix is wrong
- Adding only an option to the form would fail server validation.
- Allowing it in PHP alone would fail the database enum constraint.
- Editing `schema/001_schema.sql` would conflict with the repository rule that schema additions go through the single additive migration.

## Components
- `clinic-base/register.php`: adds the choice to the existing Gender select.
- `clinic-base/actions/register.php`: accepts the value in patient validation.
- `schema/002_migrate.sql`: extends `patient.Gender` while retaining existing values and the column name.
- `tests/test_issue187.php`: checks validation and database round trip.
- `tests/ui_issue187.mjs`: checks selection and full registration in Chromium.

## Breaks or needs follow-up
Any existing database must have the `ALTER TABLE` from `schema/002_migrate.sql` applied before this form ships; only `ie4727db_test` got it through `tools/db_reset.php --test`. The live server is not in strict SQL mode, so without the migration "I'd rather not disclose" is stored as an empty string with only a "Data truncated" warning, and the patient's choice is silently lost (found in review on 2026-10-17).

## Problem and constraints
Issue #187 asks for a non-disclosure option. The adopted schema defines `Gender` as an enum, so the new literal requires a migration. `AGENTS.md` limits schema additions to `002_migrate.sql`; the issue's request to update the schema file is fulfilled there rather than by modifying the fixed `001_schema.sql`.

## Alternatives considered
- Store `Other` for this choice: rejected because it would misrepresent the patient's selection when displayed.
- Change the column to free text: rejected because it broadens allowed data beyond this issue.

## Trade-offs
The four permitted values appear in both the server validation rule and the database enum. A future choice must update both.

## Key parameters
The stored value is exactly `I'd rather not disclose`; the existing values remain `Male`, `Female`, and `Other`.

## Assumptions
No special display label is needed because the doctor visit page displays the escaped stored value directly.

## Edge cases
An empty or unknown value still fails the patient registration rule. Existing gender values remain valid.

## Not verified
No assistive technology was used for a manual screen-reader pass.

## Changes outside the scope
The PHP and Chromium tests and this decision record are required verification artifacts. No content page was added.

## How it was verified
`php tests/run.php test_issue187`, `node tests/ui_issue187.mjs`, and `php tests/run.php` verify the new choice against `ie4727db_test`. Before and after screenshots at 1280×800 and 390×844 are under `UIPROBLEMS/after/iter7/issue187-gender/`.

## To change this
Update the form option, validation rule, enum migration, and regression tests together.

## Rollback
Remove the form and validation options only after ensuring no patient row stores this enum value; narrowing the enum with such rows present would lose data.
