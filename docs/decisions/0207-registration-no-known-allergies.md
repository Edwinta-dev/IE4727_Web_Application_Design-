Status: implemented · Issue: #207 · Date: 2026-10-27

## In short

Patients can select No Known Allergies when creating an account instead of typing a placeholder such as NA or NIL.

## Problem and constraints

The existing registration form has a free-text `Allergies` field. The fixed `patient.Allergies` column contains JSON, and the existing account model encodes an array before writing it. The checkbox must also work when JavaScript is unavailable or a different field fails server validation.

## Main design choice

Submit a separate checkbox value and let `actions/register.php` replace the allergy text with `No Known Allergies` for patient registration. This was chosen over a hidden field or treating an empty entry as no known allergies because the checkbox expresses the patient's choice directly. The server remains authoritative even if the text field is empty or changed in a crafted request. JavaScript fills and locks the visible text area for immediate feedback; PHP restores both controls after a validation redirect.

## Traps

- A read-only text area still submits its value, but JavaScript may be disabled or the request may be crafted. The handler must use the checkbox to set the canonical value.
- The `Allergies` column accepts JSON. The existing patient account path must continue to encode the canonical phrase as an array before persistence.
- A validation redirect must retain the checkbox state without retaining passwords.

## Key parameters

- Checkbox form field: `NoKnownAllergies`, checked value `1`.
- Canonical allergy entry: `No Known Allergies`.
- Stored value for a checked patient registration: `["No Known Allergies"]` as JSON in `patient.Allergies`.

## Assumptions

- The checkbox applies only to patient registration; the existing doctor registration fields and validation remain independent.
- An unchecked checkbox leaves the existing free-text allergy behavior intact.

## Alternatives considered

- Disable the text area and rely on a hidden field: disabled controls are not submitted, and the hidden value could diverge from the checkbox.
- Treat an empty allergy field as no known allergies: an accidental omission would become an affirmative medical statement.

## How it works

The checkbox sits beside the patient allergy entry. Checking it saves any typed text in memory, shows the canonical phrase, and sets the text area read-only. Unchecking restores editable text. On POST, a checked patient value takes precedence; the existing patient account path converts the phrase to an array and stores it as JSON. The validation redirect saves the checkbox state and renders the phrase read-only again.

## Edge cases

- With JavaScript off, the server accepts a checked box and ignores the text area value.
- A failed registration preserves the checked box and canonical text.
- Doctor registration does not apply the patient checkbox to its account data.

## Components

- `clinic-base/register.php`: checkbox, restored state, and patient guidance.
- `clinic-base/actions/register.php`: patient-only canonical value before validation and persistence.
- `clinic-base/assets/app.js`: text area toggle and typed-value restoration.
- `clinic-base/assets/css/style.css`: checkbox alignment, read-only state, and keyboard focus ring.
- `tests/test_registration_allergy_checkbox.php`: registration source checks.
- `tests/ui_issue207.mjs`: browser toggle, validation redirect, JavaScript-off registration, and JSON persistence.

## Trade-offs

The canonical phrase is stored as a one-element JSON array, matching how this form already stores listed allergies. Other parts of the app must interpret the phrase as a declaration of no known allergies.

## Rollback
