Status: implemented · Issue: #198 · Date: 2026-10-16

## In short
The About Us photo on the home page was a 2 MB PNG. It is now a 960 by 720 JPEG of about 89 KB, the same picture and shape, in line with the other photos on the site. A new test fails if any page image grows past 250 KB again.

## How it works
1. The original photo (1448 by 1086 pixels, about 2 MB) was scaled down to 960 by 720 pixels, twice the width the About Us column shows on a large screen, so it stays sharp on high-density screens.
2. It was saved as a JPEG at quality 82, which suits photographs far better than PNG.
3. The home page now points at the new file and states its real size, so the browser reserves the right space before it loads and the layout does not jump.
4. The old PNG was deleted.
5. A test checks every image in the site's image folder and fails if any is over 250 KB, so an unoptimised export is caught before it ships.

## Main design choice
JPEG at 960x720 rather than WebP. WebP would be smaller still, but every other photo in `clinic-base/assets/img` is JPEG, there is no image tooling in this environment that writes WebP (PHP has no GD here; the conversion used Windows `System.Drawing`), and 89 KB is already below the existing photos (largest 119 KB). WebP would win if images became a measurable part of page weight.

## Traps: why the obvious fix is wrong
- Keep the `width`/`height` attributes equal to the file's real pixels (960x720). The CSS sets `aspect-ratio: 4 / 3`, but the attributes still drive the browser's space reservation before CSS loads.
- Do not raise the 250 KB budget in `tests/test_issue198.php` to let one large file through; re-export the file instead.

## Components
- `clinic-base/assets/img/about-clinic-consultation.jpg` - new 960x720 JPEG.
- `clinic-base/index.php` - About Us `<img>` source and dimensions.
- `tests/test_issue198.php` - image size budget and the About Us reference.

## Breaks or needs follow-up
None. `about-clinic-consultation.png` is deleted; nothing else referenced it.

## Problem and constraints
Code review of #170: a 2 MB PNG photo on the home page, while the other photos are 75-120 KB JPEGs. AGENTS.md forbids CDNs and image libraries in the app, so the file itself must be small.

## Alternatives considered
- `srcset` with two sizes - rejected: the column never exceeds about 480 CSS pixels, so one 2x file covers it.
- Keeping the PNG and lazy-loading it - rejected: it was already `loading="lazy"`; the size was the problem.

## Trade-offs
JPEG quality 82 adds slight compression artefacts that are not visible at display size.

## Key parameters
- Output 960x720, JPEG quality 82: chosen for a roughly 480 px wide column at 2x density.
- Budget 250 KB (`tests/test_issue198.php::PAGE_IMAGE_MAX_BYTES`): about twice the largest existing photo.

## Assumptions
- The About Us column stays at most about half of a 1280 px layout; a full-width layout would need a larger export.

## Edge cases
- Handled: any future image over budget fails the suite with its file name and size.
- Not handled: SVG files are not checked.

## Not verified
- The page was not viewed in a browser after the change; the image was checked visually as a file.

## Changes outside the scope
None.

## How it was verified
`tests/test_issue198.php` and `tests/test_index.php` pass. The new file was opened and checked visually; its size is 89,467 bytes.

## To change this
To serve WebP, export one beside the JPEG and wrap the `<img>` in a `<picture>` with a WebP `<source>`; cost: two files to keep in step.

## Rollback
Reverting restores the PNG and the old dimensions; the size test reverts with it.
